# 初期版の設計判断

## 実装したルール

- 同一ブラウザのHttpOnly Cookie（24時間）で参加者を識別する。表示名は最大30文字。同一名は許可し、内部IDで区別する。
- 管理者は別のログインセッションを使用する。操作APIは管理者権限とOriginを検証する。WebSocketもCookieとOriginを検証する。
- ポーズ役は担当回数が最も少ない参加者からランダムに選ぶ。未経験者がいる間は同じ人に重複して割り当てない。
- ラウンド準備で受付を閉じ、全員の接続と準備完了を確認してから管理者が開始する。
- 設定はラウンド準備時に複製する。保存後の変更は進行中のラウンドへ影響しない。
- 試行したラウンドはスキップ・中止も含めて設定ラウンド数に数える。最後に管理者が最終結果へ進む。
- 「次のグループを受付」で名簿を空にして新イベントを作る。旧イベントのデータはSQLite内に保持する。

## 姿勢・投影・判定

MediaPipeの関節番号11〜16、23〜28に対応する肩・肘・手首・腰・膝・足首の12点を使用する。頭は球体で表示し、ポーズ役の3D表示には目の2点と口の曲線を追加する。観察者のお手本・カメラの重ね描画・結果の3D表示では目と口を表示しない（顔は採点・関節間隔判定の対象外）。左右は人物自身を基準にし、映像を鏡像化しない。

3DのY軸は上、正面は+Z。胴体付近を注視点とする透視投影を行う。手足の投影長、左右の対応関節間隔、および表示する12関節点の全66組の距離が設定値を満たす視点を最大300回まで生成し、不可能な場合は準備を失敗させて管理者へ通知する。全関節点の最小間隔は投影後の全高に対する比率（`min_keypoint_separation`、初期値0.08、範囲0〜0.3）で指定する。0は追加の全組み合わせ条件を無効化する。設定はデフォルト保存でき、次のラウンドの準備から適用する。古い保存設定に項目がない場合は初期値を補う。この除外判定は幾何学的な近似であり、身体の表面による遮蔽を完全に計算するものではない。

モデルは1フレーム最大4人を検出する。検出された人物の肩・腰の中心と画面中央との距離が最小の人物1人だけを採点する。中央に複数人が重なると判定対象が入れ替わり得る。人物の永続的な追跡や顔認証は行わない。

映像の縦横比を補正して正方座標に変換し、判定対象の可視点の重心とRMS半径で平行移動・スケールを正規化する。正規化座標距離、手足の方向差、関節角度差を各関節へ加算し、その平均が最も低い関節を全体スコアとする。選択された可視関節すべてが閾値を通る必要がある。回転と左右反転は補正しない。

「隠れた関節を除外」ではconfidenceが低い関節を対象外にするが、最低可視関節数を満たす必要がある。「全関節必須」では選択したすべての関節にconfidenceを要求する。

サーバー受信時刻を計時と保持時間の基準にし、端末時計は採用しない。1秒を超えて判定フレームが来ない場合や、WebSocketが切断した場合は同時成立の保持時間をリセットする。達成保持方式では既に確定したクリアは維持する。

## 保存と復旧

SQLiteの `documents` に現在イベント、イベント別アーカイブ、デフォルト設定をJSON保存する。ラウンドにはポーズ・視点・判定設定・完了時刻・各人の結果を記録する。`sessions` にはトークンのSHA-256ハッシュと有効期限を保存し、生トークンはDBへ保存しない。画像や連続映像、採点用の連続関節座標は保存しない。

準備状態・判定中スコア・接続状態はメモリ内にのみ保持する。サーバーが再起動した場合は中途ラウンドを `server_restart` として中止し、結果画面から再開する。複数workerには対応しない。

## 実機で検証する項目

- 最低対応OSの決定、iPhone Safari / Android Chromeでのモデル起動とGPU/CPU fallback。
- 縦向き・横向きの映像、背面カメラ選択、画面復帰時の再試行。
- 正面・側面・背面での左右推定、遮蔽、服装・照明・体格差。
- 暫定65%の閾値と既定視点範囲で、全ポーズに実際に到達可能な解があること。
- 50台でのモデル初回配信とWi-Fi負荷、端末ごとの発熱・電池消費。

既定のポーズは全身を使う24種類の共通プールへ拡張した。難易度別の分類は行わない。定義・関節の検証・視点生成は [ポーズプール](Pose_Pool.md) を参照。参加者の動作と認識精度は会場で検証する。

- TypeScriptの型検査と本番ビルドに合格。

## LAN起動と参加URL

`npm start`（`python -m server`）はHTTPSを8443番、証明書設定ページをHTTPの8000番で全IPv4インターフェースに待ち受け、起動時にデフォルト経路のLAN IPを検出する。外部IP確認サービスには問い合わせず、UDPソケットの経路選択結果を利用する。ルートがない場合はホスト名のIPv4解決へフォールバックする。

HTTPとWebSocketの状態配信に参加URLを含め、管理者がlocalhostでアクセスしてもQRにはLAN IPを使用する。アクセス元URLがLAN IPやHTTPSのホスト名なら、そのホスト名とポートを保持する。`POSE_LAN_IP` と `POSE_PUBLIC_URL` で手動指定できる。検出できない場合はlocalhostを配布せず、管理者が参加URLを入力する。Docker内のIPはホストLAN IPではないため、Composeでは引き続きHTTPSの外部ホスト名を使用する。

## LAN内HTTPSと会場CA

通常起動はHTTPSを使用する。初回にOpenSSLで会場CA（RSA 3072 / SHA-256、5年有効）を作成し、サーバー証明書（RSA 2048 / SHA-256、90日有効、serverAuth EKU）へ署名する。SANには現在のLAN IP、localhost、ループバックIP、明示した公開ホスト名を含める。サーバー証明書は残り7日未満、IP変更、検証失敗時に再発行する。会場CAを黙って再生成することはしない。

HTTP配布ページは別の軽量HTTPサーバーで動き、静的な設定案内と公開CAだけを返す。ゲームAPIは426、秘密鍵や任意のファイルパスは404となる。管理者ログイン、ゲーム通信、推論資材はHTTPS、リアルタイム通信はWSSで利用する。各端末のCA登録・信頼操作はOS側で1回必要。証明書のSHA-256指紋を起動ログと設定ページに表示する。

公開認証局の証明書がある場合は従来のDocker/Caddy構成か、起動時の `--ssl-certfile` / `--ssl-keyfile` を利用する。その場合は端末へのローカルCA登録は不要。

棒人間の色は `frontend/src/skeleton-style.ts` に集約し、左半身・右半身・中央に緑・青・シアンの3色を使用する。顔、顔から肩への線、肩同士・腰同士の線を中央グループとする。2Dお手本の頭は頭・肩から作る図形で、カメラ上の頭の大きさは取得できる場合に目・口のランドマークを参考にする。観察者には頭の球体だけを描画する。
