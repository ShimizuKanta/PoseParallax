# Pose Parallax

スマートフォンのカメラで仲間のポーズを見ながら、お手本と一致する視点を探す協力ゲームです。iPhone / AndroidのWebブラウザを対象にしています。

画面は日本語・英語を切り替えられます。プレイ中はカメラを大きく表示し、お手本の拡大と「詳細」から全情報を確認できます。[画面と言語の案内](docs/UI_Guide.md)

起動方法・対応端末・スマートフォンからの参加・通信と保存するデータは [利用ガイド](docs/Getting_Started.md) を参照してください。

## 初期版の範囲

- 2〜50人、1ゲーム進行。QR・表示名で参加、管理者がグループを切り替え。
- 腕・脚・胴体の傾き・ひねりを使う24種類の3Dポーズを、1つの共通プールからランダム選択。ドラッグで回転表示。観察者には個別の2Dお手本。[ポーズ一覧](docs/Pose_Pool.md)
- 背面カメラ、端末内の姿勢推定、画面中央の人物の採点。画像は送信・保存しません。
- 「一度達成すれば確定」（標準）と「全員同時に一致」。判定条件・視点条件を管理者が保存。
- 全員準備完了後に管理者が開始。時間切れ、除外、中止、スキップ、終了、再接続。
- SQLiteへ結果・参加者・ラウンドごとの設定と視点を保存。次のグループを始めても過去データを保持。

## LAN内でHTTPS起動

Python 3.11以上、Node.js 22.12以上（22系推奨）、OpenSSLが必要です。

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock
npm ci
npm run assets
npm run build
npm start
```

起動時にLAN IPを自動検出し、会場専用の認証局（CA）とHTTPS証明書を作成します。手動で証明書を用意する必要はありません。初回生成後は同じ会場CAを再利用し、IP変更や期限接近時はサーバー証明書だけを更新します。

- **初回の端末設定**：`http://検出したLAN-IP:8000/`
- **ゲーム**：`https://検出したLAN-IP:8443/`
- **管理画面**：`https://検出したLAN-IP:8443/admin`

`0.0.0.0` で待ち受けるため、同じLANの端末から接続できます。実際のURLと会場CAのSHA-256指紋は起動ログに表示します。会場ネットワークでTCP 8000と8443を許可してください。HTTP側は証明書設定案内・公開CA証明書の配布だけを行い、ゲームやログインAPIは提供しません。

### スマートフォンで最初の1回だけ行う設定

最初にHTTPの端末設定ページを開きます。そこにダウンロードボタンとOS別の手順があります。登録する前に主催者が案内したページであることを確認してください。

- **iPhone / iPad**：Safariで会場CAをダウンロード → 設定の「一般 → VPNとデバイス管理」でプロファイルをインストール → 「一般 → 情報 → 証明書信頼設定」で該当CAの完全な信頼を有効にします。[Apple公式手順](https://support.apple.com/ja-jp/102390)
- **Android**：会場CAをダウンロード → 設定の「証明書をインストール」から「CA証明書」として登録 → Chromeを開き直します。設定名は機種で異なります。[Google公式手順](https://support.google.com/pixelphone/answer/2844832?hl=ja)

その後、設定ページの「ゲームを開く」または「管理画面を開く」を押します。証明書の警告がなくなったことを確認して、カメラを許可してください。PCで管理画面を使う場合も会場CAをOSまたはブラウザの信頼済みルート証明書に登録します。端末の証明書登録はブラウザから自動では行えません。

管理画面のQRは通常HTTPSのゲームURLです。「初期設定QRを表示」で、証明書の登録がまだの参加者にHTTPの設定ページを案内できます。

### 管理と起動オプション

- 管理者パスワードは初回起動で `data/admin-password.txt` に生成します。`POSE_ADMIN_PASSWORD`（12文字以上）でも指定できます。
- 保存先は `data/pose.sqlite3`、会場CAと証明書は `data/tls/`。`POSE_DATA_DIR` で保存先を変更できます。
- **`data/tls/root-ca-key.pem` は会場CAの秘密鍵です。配布しないでください。** 設定ページが配布するのは公開CA証明書だけです。秘密鍵の権限は600、保存ディレクトリは700とし、Git管理対象外にしています。
- HTTPSポート変更：`npm start -- --port 9443`。端末設定ページのポート変更：`npm start -- --setup-port 8080`。配布ページを無効にする場合は `--setup-port 0`。
- IPの指定：`POSE_LAN_IP=192.168.21.130 npm start`。公開URLの指定：`POSE_PUBLIC_URL=https://pose.example.com:8443 npm start`。IPやホスト名が証明書のSANへ反映されます。
- 既存証明書を使う場合：`npm start -- --ssl-certfile deploy/certs/fullchain.pem --ssl-keyfile deploy/certs/privkey.pem`。この場合は会場CAの生成・HTTP配布ページを起動しません。
- CAの有効期限は5年、サーバー証明書は90日です。CAを紛失・更新した場合は各端末で再登録が必要です。ゲームデータと一緒に安全な場所へバックアップしてください。

画面編集時は `npm run start:http` と別のターミナルで `npm run dev` を実行します。Viteの `/api` と `/ws` はHTTPのポート8000へ転送されます。**開発用HTTPモードではスマートフォンのカメラは利用できません。** 通常のHTTPS起動と同時には実行しないでください。

## 公開認証局の証明書を使う会場運用（Docker）

参加者の端末へ会場CAを登録したくないイベントでは、管理しているドメインと公開認証局の証明書を使う次の構成にできます。

インターネット接続は利用可能とします。アプリ・ゲームデータは会場内サーバーで動きます。推論モデルとWASMもビルド時に取得してサーバー内に配置するため、プレイ中のCDNアクセスは不要です。

1. 会場のスマートフォンが接続できるWi-FiとサーバーLAN IPを用意します。Wi-FiからサーバーへのTCP 443接続を許可してください。
2. 例として `pose.example.com` をサーバーのLAN IPへ名前解決できるようにします。実際に管理しているホスト名を使用してください。
3. そのホスト名に対応する、iPhone / Androidで信頼されるTLS証明書を用意します。会場管理者から取得するか、管理しているドメインのDNS認証などで事前発行してください。
4. 証明書チェーンを `deploy/certs/fullchain.pem`、秘密鍵を `deploy/certs/privkey.pem` に配置します。これらはGit管理対象外です。自己署名証明書を使う検証環境では、各端末で発行元CAを信頼する設定が別途必要です。
5. `.env.example` を `.env` にコピーし、`POSE_HOST` を証明書と同じホスト名に変更します。
6. 起動します。

```bash
docker compose up --build -d
docker compose exec app cat /app/data/admin-password.txt
```

`https://設定したホスト名/admin` で管理者ログインし、表示されたQRを参加者に案内します。管理者がサーバーPCで画面を開く場合も、このHTTPSのURLを使えば適切な参加QRが生成されます。参加URL欄からQRだけを変更することもできます。

Composeはアプリの8000番をホストへ公開せず、Caddyだけを公開します。アプリの転送ヘッダー信頼設定は、この構成でのみ使用してください。ゲーム状態はプロセス内で管理するため、**Uvicornは1 worker固定**です。

証明書の更新は発行元の手順で行い、ファイル交換後に `docker compose restart proxy` を実行します。Caddyの[証明書設定](https://caddyserver.com/docs/caddyfile/directives/tls)と[WebSocket対応リバースプロキシ](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)を使用しています。

## 遊び方

1. 管理者は `/admin`、参加者は `/` を開きます。同じブラウザの同じプロファイルは1人として扱います。管理者も参加する場合は別端末または別プロファイルを使用してください。
2. 2人以上集まったら管理者が「ゲームを準備」。必要に応じて先に設定を変更・保存します。
3. ポーズ役は3Dのお手本を確認して「ポーズの準備完了」。端末は持つ・置く・ポケットに入れるなど自由です。
4. 観察者はカメラを起動し、アクセスを許可します。モデルの準備後に「カメラの準備完了」。
5. 全員が準備できたら管理者が「ラウンド開始」。棒人間は緑・青・シアンの3色で、本人基準の左半身・右半身・中央を区別します。頭の球体（ポーズ役の表示には目の2点と口の曲線）、顔から肩への線、肩同士・腰同士の線は中央色です。全身を中央に映し、お手本に合う視点を探します。
6. クリアまたは時間切れで結果画面へ。管理者が次のラウンドへ進めます。

初期設定は5ラウンド、各180秒、合格65%、1秒保持、全12関節の信頼度0.5以上です。お手本の全12関節点は、全組み合わせについて全高の8%以上の間隔を確保します。管理画面の「全関節点の最小間隔 / 全高」で変更・保存でき、0でこの追加条件を無効化できます。厳しい条件で視点を生成できない場合は、条件を満たさない問題を出さずに設定調整を案内します。数値は暫定値です。会場・実機で調整し、設定画面からデフォルト保存してください。変更は次に準備するラウンドから反映されます。

画面ロックや別タブへの移動中はカメラ判定が止まります。再接続では同じ参加者へ復帰します。準備中に切断した場合は再度準備完了が必要です。同じ参加者の別タブを開くと、新しいタブを優先します。

ポーズ役を除外するとそのラウンドを中止します。観察者を除外すると残りの観察者で終了条件を再評価し、観察者が0人になった場合は中止します。サーバー再起動時も進行中ラウンドを中止として保存し、管理者が次のラウンドを準備できます。

## 実装構成

```text
frontend/src/      TypeScript UI、Three.js、カメラ、推論Worker
server/           FastAPI、WebSocket、投影・採点、状態遷移、SQLite
scripts/          モデル・WASM配置とテストサーバー
tests/            Pythonテスト、Playwrightのブラウザテスト
deploy/           HTTPSリバースプロキシ設定
docs/             企画書・実装仕様・初期版の設計判断
```

初期版は仕様書の技術構成例にあるYOLO / ONNX Runtime Webではなく、[MediaPipe Pose Landmarker](https://ai.google.dev/edge/mediapipe/solutions/vision/pose_landmarker/web_js)を使用します。Worker内でGPU delegateを試し、初期化に失敗した場合はCPUへ切り替えます。WebGPU優先の実装ではありません。推論は最大約8回/秒、採点の上限は10回/秒、状態配信は2回/秒です。

## 検証

```bash
.venv/bin/pytest -q
npm run build
npx playwright install chromium
npm run test:e2e
```

Playwrightは専用の一時DBとテスト用パスワードを使い、実データを変更しません。Chromiumの疑似カメラで実モデルの読み込みと推論処理を検証し、クリア動作はテスト側から既知の関節座標を送って確認します。実際の人間に対する精度を保証するテストではありません。

実機での精度・速度・発熱、iOS Safari / Android Chromeのカメラ継続動作、50台が接続する会場Wi-Fiでの負荷は別途確認が必要です。画像アルバム、チームの同時進行、イベント横断ランキングは初期版に含めません。
